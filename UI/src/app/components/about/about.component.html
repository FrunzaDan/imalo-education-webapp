About this application

Imalo Education Webapp is a small full-stack learning project: an Angular single-page frontend talking to an ASP.NET Core Web API, which persists data in SQL Server through raw ADO.NET calls — no ORM, no stored procedures, just parameterized SQL commands. It tracks scholars, their parents, their weekly pickup times, and their daily attendance (lunch and transport).

Running it locally

The database is a containerized SQL Server (Azure SQL Edge, which also runs natively on Apple Silicon). Started by hand, that's: 

docker pull mcr.microsoft.com/azure-sql-edge

docker run -e "ACCEPT_EULA=1" -e "MSSQL_SA_PASSWORD=MyStrongPassw0rd?" -p 1433:1433 --name sqlserver --platform linux/arm64 -d mcr.microsoft.com/azure-sql-edge

On macOS and Linux the API always uses that container. On Windows it uses the container if it answers within 3 seconds, and otherwise falls back to a locally installed SQL Server (Windows authentication); the choice is logged at startup.

Once the container is up and the schema is deployed (see Database below), the two remaining pieces both need to be started:

  • API — the ASP.NET Core Web API project at http://localhost:5244, run with dotnet run (or from your IDE). It serves the REST endpoints and talks to SQL Server over ADO.NET.
  • Angular frontend — the SPA at http://localhost:4204, run with ng serve / npm start. It calls the API over plain HTTP for every scholar and attendance operation.

Both must be running at the same time — the UI has no data of its own beyond forms, validation, and the static school list; everything else it shows comes live from the API. If the API isn't reachable, the UI notices within a few seconds (it polls a lightweight /health endpoint) and shows a plain "API is not running" message in place of the page, instead of failing silently or showing stale data.

Build & run scripts

Two scripts at the repository root wrap all of the above so nothing needs to be pieced together by hand:

  • ./build.sh — a CI-style, one-shot build: restores and builds the .NET API, runs its test suite, builds the SQL database project, then installs, format-checks, builds and tests the Angular app. It doesn't start anything; it just proves everything compiles and the tests pass.
  • ./run.sh — the actual local dev environment. It makes sure Docker is running (starting Docker Desktop on macOS if needed), starts the Azure SQL Edge container if it isn't already up (pulling and creating it on first run), builds the database project and publishes its schema straight into that container, then launches the API in the background and the Angular dev server in the foreground. Ctrl+C stops both.

run.sh is safe to re-run any time: an existing, already-initialized database is simply left alone (schema deploys are a diff, not a wipe-and-recreate — so any scholars you've added through the UI survive a re-run), and a stopped container is restarted rather than recreated. The container is shared with the sibling apps; each app uses its own database.

Database

The schema lives in its own SQL Server Database Project (a .sqlproj), not in migration scripts run by the API. run.sh builds that project into a .dacpac and deploys it with sqlpackage, retrying automatically until the freshly-started container starts accepting connections. On a fresh server that one publish creates the database and everything in it. This deploy is a diff against the container's current state, so it's idempotent — running it again against an already-initialized database changes nothing — and it's allowed to rebuild already-populated tables when a schema change requires it, since this is disposable local dev data, not a production database that needs that guardrail.

The schema has five tables:

  • Scholar — one row per scholar: name, school, grade, and birth date, keyed by a server-generated ScholarId (GUID).
  • ScholarParent — up to two rows per scholar, one for the mother and one for the father: name and phone number, each optional but at least one of them set.
  • ScholarPickupSchedule — one row per scholar, storing their Monday–Friday pickup times as a JSON document.
  • ScholarAttendance — one row per scholar, storing every recorded day's presence, lunch/transport selection, and cost as a JSON document.
  • ScholarAuditLog — one row per change to a scholar (created, edited, deleted). It deliberately has no foreign key to Scholar, so a scholar's history survives their deletion.

Deleting a scholar cascades to their parents, pickup schedule, and attendance. The JSON columns are checked to hold valid JSON; their shape is enforced by the API's typed models. Schools (name, color, lunch and transport prices) aren't in the database at all — they're static reference data the UI loads from schools.json.

There's no seed data: the database starts empty, and the generator below fills it.

No authentication

Unlike the sibling customer and employee apps, there's no login here — every API endpoint is open. That's a deliberate choice for an app that only ever runs locally, not an oversight. The API still only accepts browser requests from the Angular app's own origin (a configured CORS allow-list).

Data access & errors

All reads and writes go through raw ADO.NET SqlCommands in ScholarDataAccess, with every input passed as a typed, bound parameter — nothing is built by string-concatenating SQL. Saving a scholar writes the scholar, pickup schedule, and parents in one transaction; saving attendance replaces the scholar's whole list in one race-free statement. All of it is exposed through ScholarsController, a plain REST API under /api/scholars.

Every error the API returns is an RFC 9457 Problem Details response — 400 for invalid input (such as lunch selected on a day the scholar wasn't present), 404 for an unknown scholar — which the UI reads to show a specific message next to the control that failed; anything unexpected is logged once and returned as a 500.

Console-logged API calls

Since this is a showcase app, every HTTP call the Angular frontend makes to the API is mirrored to the browser's devtools console via apiLoggerInterceptor, a functional HttpInterceptorFn registered in app.config.ts. Open devtools (F12 or Cmd/Ctrl+Shift+I) and watch the Console tab while using the app:

  • A blue → METHOD url line is logged when a request goes out, with its request body attached.
  • A green ← METHOD url status (Nms) line is logged when the response comes back successfully, with the response body and how long it took.
  • A red ✖ METHOD url status (Nms) line is logged instead if the request fails.

Nothing is logged during server-side rendering — only in the browser.

Generate test scholars

This is test data. The button below registers 20 fictitious scholars through the same POST /api/scholars endpoint the Add scholar form uses — each with a random name, a school from the school list, a grade from 1 to 4, a birth date that makes them 5 to 12 years old, a Monday–Friday pickup schedule between 11:00 and 13:45 on the quarter hour (so it lands on real slots of the Pickup time chart), a mother (always) and a father (about half the time), each with a name and phone number. It exists purely so there's enough data to try out the dashboard, the attendance pages, and the charts locally.

Each test scholar also gets attendance from July 2024 to September 2026 (through POST /api/scholars/<scholarId>/attendance, the same endpoint the per-scholar attendance page saves with): about 7 in 10 weekdays recorded, with lunch and transport selected at random and priced from that scholar's school — never transport without lunch, and no transport in the July–August summer break.

What you can do in the UI
  • See the dashboard: key figures, today's pickups, upcoming birthdays, and recent activity.
  • Browse the scholar table: search by name, sort by name, school, grade, or birth date.
  • Add a new scholar, or edit an existing one, through a validated form (name, school, grade, birth date, parents, pickup times); leaving a form with unsaved changes asks first.
  • Open a scholar's details page for their parents, pickup schedule, and audit trail.
  • Delete a scholar (with a confirmation prompt), or select several at once with row checkboxes and delete them together.
  • Export the scholar table to a CSV file.
  • See every scholar's pickup times laid out on a day-by-day Gantt chart, in 15-minute slots colored by school.
  • See every scholar's attendance for a month on one grid, and open a scholar to view and edit their month day by day; both export to CSV.
  • Explore the charts: the month at a glance (attendance rate, scholars per day, revenue, lunch take-up), the month day by day, the year (attendance calendar, revenue by month), and the scholars (pickup rush hour, classes, schools).
  • Browse a global, paginated audit trail of every scholar change (create/edit/delete) across the whole system, newest first, and clear it.
